Catálogo y actividad del servidor

Requisitos técnicos para empezar a recibir catálogos de las organizaciones oficiales y conservar el registro de cambios que protege a la comunidad.

Versión: 1.0  ·  Fecha: 19 de noviembre de 2026  ·  Cliente: mini-app Bazar/Trueque (Nahua)  ·  Estado: listo para integrar

La app ya funciona sin servidor con un catálogo local. Este documento define lo que el servidor tiene que exponer para que el catálogo llegue firmado, versionado y con historial: qué endpoints, qué campos, cómo se versionan los cambios, qué se guarda para auditar fraudes y cómo sabe el usuario si está viendo información actualizada o vieja.

1. Qué resuelve el servidor

Catálogo con stock real

Las organizaciones oficiales publican productos con existencias. La app debe poder comprar sabiendo cuántas piezas hay y sin volver a descargar todo el catálogo cada vez.

Historial de cambios

Cada alta, baja, cambio de precio o de stock queda registrado con fecha, valor anterior y valor nuevo. Es la prueba para reclamar un cobro o reportar un engaño.

Lo que ya está implementado en la app
  • Cliente de catálogo versionado: instala una foto completa una vez y luego aplica sólo parches.
  • Reconstrucción de cualquier versión anterior (incluidos productos retirados).
  • Pantalla de actividad: muestra «precio $620 → $580», «stock 4 → 1», altas y bajas, con fecha.
  • Indicador de frescura: «catálogo al día» o «catálogo sin actualizar desde hace X», con confirmación extra antes de cobrar cuando está viejo.
  • Reportes de artículos y usuarios con motivo y nota, guardados con fecha.

2.2 Producto

{
  "id": "c1",
  "storeId": "coop",
  "title": "Taza de cerámica del campus",
  "priceCents": 6500,
  "stock": 8,
  "emoji": "☕",
  "tag": "Fijado",
  "createdAt": 1793000000000,
  "updatedAt": 1795000000000
}
Dinero en centavos enteros. Nunca decimales ni cadenas con formato. 6500 son $65.00. Así se evitan errores de redondeo al comparar precios históricos.

Stock. Entero ≥ 0. 0 significa agotado, no «borrado»: el producto sigue visible con la etiqueta «Agotado». Un producto que la tienda retira del catálogo va en removed, no se pone en stock 0.

2.3 Parche (unidad de cambio)

{
  "version": 5,
  "at": 1795600000000,
  "added":   [ { "id": "c9", "storeId": "coop", "title": "Pluma", "priceCents": 1500, "stock": 40, "emoji": "🖊", "tag": "Nuevo", "createdAt": 1795600000000 } ],
  "removed": [ "c4" ],
  "updated": [ { "id": "c1", "priceCents": 7000, "stock": 3 } ]
}
  • updated lleva sólo los campos que cambiaron, más el id.
  • Los parches son inmutables y consecutivos: la versión N+1 existe una sola vez y no se edita.
  • Un producto retirado no revive con el mismo id. Si vuelve, se publica con un id nuevo.

3.1 GET /v1/catalog/head

{ "version": 5, "serverTime": 1795600000000, "generatedAt": 1795599000000, "validUntil": 1795685400000 }

3.2 GET /v1/catalog?full=1

{ "version": 1, "serverTime": 1795600000000, "stores": [ ... ], "products": [ ... ] }

3.3 GET /v1/catalog/delta?since=4

{ "to": 5, "serverTime": 1795600000000, "patches": [ { "version": 5, "at": 1795600000000, "added": [], "removed": [], "updated": [] } ] }

Sin cambios: { "to": 4, "patches": [] }. La app lo interpreta como «estás al día» y no descarga nada más.

3.4 POST /v1/orders

{
  "orderId": "ord_01J...",          // idempotencia: repetir la llamada no cobra dos veces
  "storeId": "coop",
  "productId": "c1",
  "quantity": 1,
  "unitPriceCents": 6500,
  "catalogVersion": 5,              // versión con la que el usuario vio el precio
  "buyer": { "userId": "u_123", "phone": "3121234567" }
}
{
  "status": "ok",
  "orderId": "ord_01J...",
  "chargedCents": 6500,
  "stockLeft": 7,
  "receiptUrl": "https://.../recibos/ord_01J.pdf"
}
Precio y stock se validan en el servidor. Si unitPriceCents ya no coincide con el precio vigente, responder 409 price_changed con el precio nuevo; la app muestra el cambio y pide confirmación. Si no hay stock, 409 out_of_stock.

4. Versionado: reglas duras

  1. Versión monótona. Cada parche sube exactamente 1. Sin huecos y sin repetir.
  2. Parche inmutable. Corregir un error es un parche nuevo, nunca editar el anterior.
  3. Ids estables. Un producto conserva su id en todo su ciclo de vida. Al retirarse se va en removed.
  4. Sin reutilización. Un id retirado no se vuelve a usar, ni siquiera para el mismo producto.
  5. Delta idempotente. since=N siempre devuelve lo mismo para N. Se puede reintentar.
  6. Photo + patches. La foto completa corresponde a una versión concreta y los parches empiezan en la siguiente.

5. Registro de actividad (auditoría)

El objetivo es poder responder: ¿quién cambió qué, cuándo, de cuánto a cuánto y por qué? Sirve para reclamar un cobro, detectar cambios de precio justo antes de una compra y frenar publicaciones engañosas.

Se guardaDetalle
AltaId, tienda, título, precio inicial, stock inicial, fecha, usuario que publicó.
Cambio de precioPrecio anterior, precio nuevo, fecha, usuario y motivo declarado.
Cambio de stockStock anterior, stock nuevo, fecha y origen (venta, ajuste, devolución).
BajaQuién la pidió, fecha y motivo (descontinuado, error, sanción).
VentaOrden, comprador, precio cobrado, versión del catálogo usada.
ReporteObjetivo, motivo, nota, fecha, estado de revisión.

Retención

Mínimo 24 meses para precios y stock; 36 meses para bajas y reportes. La app conserva localmente lo que ya descargó, pero el servidor es la fuente de verdad.

Integridad

Cada evento lleva un hash que encadena con el anterior (como un libro contable). Si alguien altera un registro viejo, la cadena deja de cuadrar y se detecta.

5.1 Evento de actividad

{
  "id": "evt_01J...",
  "at": 1795600000000,
  "storeId": "coop",
  "productId": "c1",
  "productTitle": "Taza de cerámica del campus",
  "type": "price",                 // added | price | stock | removed | restored
  "fromCents": 6500,
  "toCents": 7000,
  "actor": "coop-admin",
  "reason": "Ajuste de temporada",
  "catalogVersion": 5,
  "prevHash": "9f2c...",
  "hash": "b71e..."
}

5.2 GET /v1/catalog/changes?since=N

{ "to": 5, "events": [ { ... }, { ... } ] }

Si no se implementa, la app puede derivar la actividad comparando los parches que ya tiene; se pierde el motivo y el actor, no el cambio de precio.

6. Frescura: ¿el catálogo está actualizado?

La app compara la versión local con /head y la hora de la última sincronización. Con eso decide qué mostrar:

EstadoReglaQué ve el usuario
Al díaVersión local = versión del servidor y última sincronización < 24 h«Catálogo al día · hace 5 min». Compra directa.
Con cambiosEl servidor tiene una versión mayor«Hay cambios sin aplicar (v4 → v5)». Invita a actualizar.
Sin actualizarÚltima sincronización > 24 h«Catálogo sin actualizar desde hace 3 días». Aviso de que puede faltar stock o haber cambiado el precio.
ActualizandoDescarga en cursoIndicador de progreso; no bloquea la navegación.

6.1 Reglas de compra según frescura

  • Al día: se cobra y se valida stock contra el servidor en el mismo paso.
  • Con cambios o sin actualizar: la app pide una segunda confirmación («el artículo puede estar agotado») antes de abrir el pago.
  • Sin conexión: se puede navegar y ver la última versión en memoria, pero la compra se bloquea hasta confirmar con el servidor.
Respuesta obligatoria en /head: incluir serverTime y validUntil. La app usa serverTime para no depender del reloj del teléfono y validUntil para marcar el catálogo como viejo aunque no haya cambios de versión.

7. Reportes y antifraude

La app ya permite reportar un artículo o un usuario con seis motivos: artículo prohibido, precio engañoso, falta de stock, actitud irrespetuosa, spam y otro. El servidor debe recibirlos, acusar recibo y permitir consultar su estado.

7.1 POST /v1/reports

{
  "reportId": "rep_01J...",
  "targetType": "listing",          // listing | user | store
  "targetId": "L_9f3a",
  "targetTitle": "Bicicleta rodada 26",
  "reason": "precio",
  "reasonLabel": "Precio engañoso o distinto al acordado",
  "note": "Me quiso cambiar el precio al llegar.",
  "reporter": { "userId": "u_123", "phone": "3121234567" },
  "createdAt": 1795600000000,
  "catalogVersion": null,
  "evidence": []                    // opcional: URLs de capturas o comprobantes
}
{ "status": "ok", "reportId": "rep_01J...", "state": "received", "slaHours": 72 }

7.2 Reglas antifraude mínimas

  • Un reporte por persona y objetivo cada 24 h; repetir el intento devuelve el reporte existente.
  • Estados: received → reviewing → resolved o dismissed, con nota interna.
  • Alertas automáticas cuando un precio sube más del 40 % en menos de 1 h o cuando un producto se retira justo después de una compra.
  • Prohibiciones: el servidor puede marcar productos y tiendas con blocked y razón; la app los oculta y conserva el historial.

8. Seguridad y operación

TemaRequisito
TransporteHTTPS obligatorio, TLS 1.2+. Sin excepciones para staging.
AutenticaciónToken por organización (Bearer) para publicar cambios. La app lee el catálogo con un token público de sólo lectura.
IntegridadFirma HMAC-SHA256 del cuerpo con un secreto compartido; la app rechaza el catálogo si no cuadra.
IdempotenciaIdempotency-Key en /orders y /reports.
Límites60 req/min por token de lectura; 10 req/min para escritura. 429 con Retry-After.
CachéETag + If-None-Match en /head y /catalog.
ErroresCódigo estable en el cuerpo (price_changed, out_of_stock, stale_version) además del HTTP.
RespaldosCopia diaria del catálogo y del registro de actividad, con prueba de restauración mensual.

9. Lo que necesito de tu lado para arrancar

  1. URL base del servidor en staging y producción (por ejemplo https://api.mitienda.mx).
  2. Token de lectura para la app y tokens de escritura por organización.
  3. Secreto HMAC (o llave pública, si prefieres firma asimétrica) para validar el catálogo.
  4. Catálogo inicial en el formato de la sección 2, con al menos una tienda y 5 productos de prueba con stock.
  5. Un parche de ejemplo (alta + baja + cambio de precio + cambio de stock) para probar el delta de punta a punta.
  6. Imágenes o emojis de los productos: hoy la app usa emoji; si habrá fotos, acordar tamaño y formato (WebP 600×600, menos de 120 KB).
  7. Contacto técnico para incidencias y una persona responsable de aprobar reportes.
  8. Política de retención confirmada (24/36 meses) y zona horaria de los timestamps (UTC en milisegundos).
  9. Ambiente de pruebas con datos ficticios; no usar precios reales en staging.

Resumen en una línea: exponer /head, /catalog?full=1 y /catalog/delta?since=N con parches inmutables que incluyan stock y precio, guardar los eventos de actividad con actor y fecha, y responder con la hora del servidor para que la app pueda decir con honestidad si el catálogo está actualizado o no.
